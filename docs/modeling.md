# Modelling — feature matrices, EDA findings and the protocol

Everything here is regenerated by `make features`. Every number quoted comes
from `artifacts/benchmarks/eda-summary.json`,
`artifacts/benchmarks/feature-shortlist.json` or
`artifacts/datasets/features-manifest.json`; nothing is hand-typed.

Feature definitions live in [`feature-catalogue.md`](feature-catalogue.md),
which is generated from `ml-service/app/research/feature_catalogue.py`. The
ablation ladder, the label and the leakage rules are pre-registered in
[`preregistration.md`](preregistration.md) §7.

## 1. What `make features` builds

```
make features
  ├── app.research.build_features    -> data/processed/features-<source>.parquet  (8 sources)
  │                                     artifacts/datasets/features-manifest.json
  ├── app.research.audit_leakage     -> exits non-zero on a leak (also runs in `make test`)
  ├── app.research.eda               -> artifacts/figures/05-eda/f05-{01..13}_*.png
  │                                     artifacts/benchmarks/eda-summary.json
  │                                     artifacts/benchmarks/feature-shortlist.json
  └── app.research.feature_catalogue -> docs/feature-catalogue.md
```

| Source | Rows | Learners | Features carried | Accuracy |
|---|---|---|---|---|
| `assistments_2009` | 250,718 | 2,968 | 11 / 44 | 0.659 |
| `assistments_2012` | 2,571,214 | 22,422 | 16 / 44 | 0.700 |
| `ednet_kt1` | 4,873,615 | 23,916 | 14 / 44 | 0.654 |
| `sim-V0` … `sim-V4` | ~153,000 each | 1,000 each | 44 / 44 | 0.662 (V0) |

**The label is `next_correct`** — the next attempt's outcome. Features describe
attempt *t* and inform the selection of attempt *t+1*, which is the decision the
system actually makes. The last attempt of every learner has no label and is
dropped rather than imputed.

**A source that cannot supply a feature writes no column for it.** `read_features()`
re-adds it as all-null on the way in, so every consumer sees one schema while
EdNet's 4.9 M rows do not carry 33 empty float columns. Absence is null, never
zero (`preregistration.md` §4).

**Per-attempt behavioural columns are not computed here.** They come from
`app.features.extract` — the same function the live backend calls over HTTP.
This file only adds what needs a *sequence*: history aggregates, session
structure and the label. There is still exactly one definition of a feature.

## 2. Leakage: what is checked and how

Defect 2 of the audit was that the pre-Phase-0 pipeline fed the simulator's own
latent `knowledge_before` and `fatigue_before` to the model. `audit_leakage.py`
runs in `make test` and fails the build. Four checks:

| Check | What it asserts | How |
|---|---|---|
| A | No `latent_*`, `probe_*` or `next_*` column is a feature; no undeclared column rides along | against the catalogue, the extractor, the legacy `BASE_FEATURES` list and every matrix on disk |
| B | A row is unchanged by deleting every row after it | rebuild the source truncated mid-learner, compare row by row |
| C | Item difficulty and the per-item RT standardisation never saw a test learner | refit with the test learners removed, compare |
| D | Every matrix has a label, no null labels, and held-out test rows | read what is on disk |

Check B is the one that matters. Reading code for `shift(1)` finds what you
thought to look for; truncating the data and demanding identical output finds a
centred window, an unshifted expanding mean, a resort, or a statistic fitted
over the whole column. `test_features.py::test_audit_catches_a_planted_lookahead`
plants a leading rather than lagging prior accuracy and asserts check B raises —
a guard never shown to fire is not a guard.

Item difficulty and `log_rt_z_item` are **population** statistics: properties of
an item estimated across training learners. Check B freezes them while it runs
(they legitimately move when the population moves) and check C asserts the
condition that makes a target-style encoding valid at all — no test learner
contributes.

## 3. What the EDA found

### 3.1 The fatigue construct does not survive contact with the data

**This is the headline finding of Phase 5 and it is a null result.**
`f05-06` plots within-session accuracy with the item's own base rate removed —
the matched-difficulty comparison the literature asks for, because raw accuracy
falls whenever later items are harder, which is a selection effect.

| Source | Slope per item | 95 % CI (learner-clustered bootstrap) |
|---|---|---|
| `assistments_2012` | +0.000077 | [−0.000125, +0.000280] — flat |
| `ednet_kt1` | +0.000165 | [+0.000004, +0.000343] — significantly **positive** |
| `assistments_2009` | not measurable | no wall clock, so no sessions |

`preregistration.md` H2 pre-committed to reducing or dropping the construct if
this was flat. It is flat, and one source improves. Fatigue is therefore **not**
carried as a validated latent state into Phase 7's gate or Phase 8's policies.
The multi-state model is knowledge, engagement and confidence.

The *speed* channel is a different story and it survives: `f05-07` shows a
significant negative slope everywhere (`assistments_2012` −0.0092
[−0.0097, −0.0087]; `ednet_kt1` −0.0018 [−0.0023, −0.0013]). Learners speed up
as a session runs. `matched_difficulty_speed_slope` stays as an L3 feature; what
is dropped is the claim that it indexes a fatigue *state*.

### 3.2 Response time is a real but small signal, and its sign is stable

Correlation of log response time with correctness: −0.096
(`assistments_2012`), −0.086 (`ednet_kt1`), −0.028 (`assistments_2009`, whose
response times are noisiest), −0.048 (simulated V0). Slow answers are wrong
answers, and `f05-04` shows the relationship holds inside every item-difficulty
tercile — so it is not an artefact of hard items taking longer.

### 3.3 Answer changing is monotone and unhelpful in the simulated interface

`f05-05`: accuracy falls with every additional option change — 0.703 at zero
changes, 0.675 at one, 0.653 at two, 0.633 at three, 0.616 at four or more.
Among single-change attempts (n = 43,703) the determinate wrong→right share is
0.675.

This does **not** reproduce the B26/B27 finding that answer changes are net
beneficial, and the reason is honest rather than interesting: the simulator
generates a change from hesitation, and hesitation is generated from low
knowledge. Nothing in the generative model makes a change *corrective*. The
archival sources carry no option-change data at all, so this question cannot be
answered offline in this project. Recorded as a limitation, not a finding.

### 3.4 RQ2: trajectory features carry a little beyond response time (simulated only)

`f05-09` reports partial correlations with the label holding response time out
of both sides. The largest are `max_deviation` −0.023 (raw −0.023),
`path_ratio` −0.021, `hover_time_max` −0.020. Their correlations *with*
response time are 0.03, 0.02 and 0.07 — so they are close to orthogonal to it,
which is the shape RQ2 predicts, at a magnitude consistent with H1's
pre-registered "+1–3 % AUC, not more."

`f05-11` is the cautionary companion. Compressing each rung to a single
logistic score, the mutual information with `next_correct` is L0 0.0232 nats,
L2 0.0034, L3 0.0006, L1 0.0002 and **L4 0.0000**; pairwise redundancy is at
most 0.0023 nats, so the rungs are near-disjoint rather than duplicating each
other. Read this as a **lower bound per rung**, not a verdict: a linear score is
the cheapest possible summary of a rung and it discards any interaction a tree
model would find — `log_rt_z_item` alone reaches 0.0042 nats on
`assistments_2012`, above what the whole L1 score scores here. What the figure
does establish is the ordering, and it is stark: correctness history dominates
every behavioural rung by an order of magnitude. Phase 6's ablation ladder
decides whether L4 clears the 2 % protocol-noise band; the honest prior after
this figure is that it will not.

### 3.5 The simulator couples signals the real world does not

Three pairs are perfectly correlated in `sim-V0` and would not be in real
telemetry: `idle_count` ↔ `visibility_changes` (r = 1.00), `focus_fraction` ↔
`idle_fraction` (r = −1.00), `time_to_first_movement` ↔
`time_to_first_selection` (r = 1.00). Each comes from a single generative
channel. The shortlist drops one of each pair and says so in the drop reason,
flagged `simulated_only` — the redundancy is a property of the generative model
and must be re-checked when real motor telemetry exists.

`redundant_pairs()` therefore requires a pair to be collinear in **every**
source that carries both. That rule is what saved `log_response_time`: it is
0.95-correlated with `log_rt_z_item` in the simulator and much less so in the
archival tables, and dropping SAINT+'s headline feature on a simulator artefact
would have been a real mistake.

### 3.6 The motor features are mostly traits, and that is a problem Phase 7 owns

`f05-10` splits each feature's variance into between-learner and within-learner
parts. The result is the opposite of convenient:

| Most trait-like (between / total) | | Most state-like | |
|---|---|---|---|
| `path_ratio` | 0.87 | `item_difficulty` | 0.03 |
| `velocity_mean` | 0.87 | `rt_drift` | 0.03 |
| `cursor_samples` | 0.75 | `auc_toward_nonchosen` | 0.04 |
| `prior_accuracy` | 0.75 | `idle_time` | 0.05 |
| `hover_time_max` | 0.72 | `visibility_changes` | 0.06 |

Most motor features are dominated by **stable learner identity**, not by the
attempt. This is not a bug — it is Phase 4's design working exactly as intended.
Breaking Defect 3 required giving each simulated learner idiosyncratic pointer
traits (speed, jitter, device, re-reading habit) drawn *independently of
ability*, and the direct consequence is that raw `path_ratio` mostly tells you
who is answering, not how they are doing.

The consequence is concrete and it is recorded here before Phase 7 starts: **a
raw motor feature is a poor state signal.** A state estimator that wants to use
them needs a within-learner baseline — the same standardisation `rt_drift`
already applies to response time, which is why `rt_drift` sits at 0.03 while raw
`log_response_time` does not. `rt_drift` and `auc_toward_nonchosen` are the two
features already in the right shape. Phase 7 should not read a high raw
`path_ratio` as hesitation.

## 4. The shortlist

`artifacts/benchmarks/feature-shortlist.json`: **36 kept, 8 dropped.**

The bar is deliberately low. This step drops what is *empty*; deciding what is
worth its privacy cost is the ablation ladder's job in Phase 6, and doing it
here on the same data would be selecting on the outcome.

| Dropped | Why |
|---|---|
| `n_options`, `skipped` | constant in every source that supplies them — a 100 % MCQ bank cannot vary the option count, and the simulated learner never skips |
| `response_time_vs_estimate`, `pause_count`, `velocity_mean` | mutual information below 1e−4 *and* non-positive permutation importance |
| `idle_count`, `idle_fraction`, `time_to_first_movement` | perfectly collinear with a better-informed twin **in the simulated source only** — re-check when real telemetry exists |

Collinearity is reported but not acted on beyond that: VIF above 10 covers
`option_changes` (97), `cursor_samples` (59), `option_revisits` (50),
`option_change_entropy` (39), `log_response_time` (34), `log_rt_z_item` (22) and
`question_number` (11). Tree models do not care and the regularised linear
models in Phase 6 handle it; dropping a construct because it correlates with a
sibling would cost the ladder a rung.

A quick `HistGradientBoostingClassifier` on the full simulated feature set,
learner-grouped, reaches **AUC 0.637** on held-out learners. That is the
sanity floor Phase 6's models must beat, not a result.

## 5. Deliberate omissions

| Skipped | Why | Add when |
|---|---|---|
| Typing dynamics (`typing_speed`, `backspaces`, `delete_frequency`) | zero coverage — the bank is 100 % MCQ (`preregistration.md` §2) | an item format requires typed input |
| Any imputation written back to a matrix | absence and measurement must stay distinguishable; median filling happens inside the MI estimator only and is never persisted | never |
| Per-source feature *selection* | a different feature set per source makes the ablation ladder incomparable across sources | never |
| A fitted per-learner session-gap threshold | 30 minutes is the log-analysis convention and session boundaries only bound a result here, they do not carry one | a result depends on the cut |
| Re-splitting anything | `splits.json` is the single source of truth; Phase 5 appended the five simulator variants and touched no archival entry | never |

## 6. Legacy — superseded, kept only as the audit's evidence

`ml-service/app/model/features.py` is the pre-Phase-0 feature list. It still
contains `knowledge_before` and `fatigue_before` — the columns of Defect 2 —
and `audit_leakage.check_legacy_features_are_not_used()` asserts both that they
are still there and that the catalogue has not re-adopted them. It is the
"before" side of the fix and nothing in the Phase 5 pipeline imports it.

`docs/model-card.md` and every metric in `artifacts-legacy-invalid/` describe
models fitted on that list and are not citable.

## 7. Learned policies (Phase 9)

Three models that choose an action rather than predict an outcome. All three
read the same vector — `app.policy.learned.context`: eight observables plus the
states the Phase 7 gate admitted, which is knowledge and its standard error and
nothing else. A rejected head has no column; `test_study3` asserts it by name.

| model | parameters | what it assumes |
|---|---|---|
| `bandit_linucb` | 120 × (11-vector θ, 11×11 inverse covariance), α = 1.0 | reward is linear in the context, separately per action |
| `bandit_lin_ts` | as above, σ = 0.1 | as above, with a Gaussian posterior |
| `rl_ppo` | `stable-baselines3` `MlpPolicy`, library defaults | the sequence matters — the only arm that optimises a return rather than an immediate reward |

**Both bandits are disjoint**: they keep one linear model per action and share
nothing between difficulty 5 and difficulty 6. With 120 actions that is a lot of
models for a short budget, and it is the first thing to change if the bandit is
visibly underfitting — an action-featurised or neural bandit is the upgrade, and
`f09-09`'s action map is where the evidence for needing one would show up.

Updates are Sherman-Morrison rank-1 rather than a solve, so a decision costs one
outer product per learner instead of a 120-fold inversion; that is what makes an
online bandit affordable inside the same closed loop the rules run in.

PPO trains against `app.rl.env.ALPEnv`, which **is** the Phase 8 closed loop
with a cohort of one — not a re-derivation of it. A second copy of the dynamics
would be a second set of assumptions to keep in step, and the first divergence
between them would be silent.
